# Operational Disruption and Hazard Intelligence Platform

Implementation plan using BELA (primary) and BLINK (optional) for place and facility linking.

Working product name: `BRAND_NAME` (default "Meridian Signal"; run a trademark check before any public launch).
Team: 1 to 2 full-stack engineers with ML experience. Duration: about 16 weeks.

## 1. Writing and engineering conventions (mandatory)

- Use a professional, neutral tone in every artifact: code comments, commit messages, docs, issue titles, UI copy, marketing copy. No slang, jokes, emojis, or hype wording.
- Never mention any AI assistant, chatbot, or AI vendor tool by name in code, comments, docs, commit messages, or UI copy. No "generated by" notes.
- Never use the em dash character (Unicode U+2014) anywhere. Use a colon, comma, parentheses, or a plain hyphen. Add a CI step that fails the build if U+2014 appears in any tracked text file.
- Every claim in the UI or marketing pages must be backed by a measurement produced in this repository or by a cited public source. No invented customers, customer logos, testimonials, awards, press mentions, or certifications. Scenario cards must be labeled "Illustrative scenario".
- This product is situational awareness, not an official warning service. Every alert, map, and report must carry the disclaimer in section 2 and must link to the original source.
- Conventional Commits, pull request template, architecture decision records in `docs/adr/`.
- Python: type hints everywhere, `ruff`, `mypy` (strict on core packages), `pytest`. TypeScript: strict mode, ESLint, Prettier. Backend core logic coverage of at least 80 percent.

## 2. Scope and constraints

**Product.** A web platform where logistics, corporate security, travel risk, facilities, and insurance teams register their sites and routes, and receive alerts when credible disruption is reported near them. Entity linking turns place names in news text (including facilities such as ports, plants, and airports) into coordinates, so reports can be matched to assets. Structured hazard feeds (earthquakes, weather alerts, fires) are fused with news into one incident picture.

**In scope:** asset upload and management, news and hazard ingestion, place and facility linking, incident detection and classification, event geolocation with uncertainty, exposure scoring, alerts and watch zones, briefings, live map, operational analytics, platform revenue analytics, authentication and authorization, marketing website.

**Out of scope:** real payments, real customer data, safety-of-life warning services, evacuation guidance, tracking of individual people, production compliance or insurance certification.

**Constraints**
- Free and open-source tooling only. Any LLM runs locally and is a 3B to 4B model from Hugging Face.
- Disclaimer (show on every alert, map, briefing, and report): "Signals are situational awareness derived from public news and public data feeds. They are not official warnings. Verify with local authorities and follow their guidance." Hazard feed operators state that automated alerts should not be used for decisions without confirmation. Preserve that message.
- Do not track, geolocate, or profile private individuals. The event classifier drops crime and incident reports whose subject is a named private person.
- Tenants, subscriptions, invoices, revenue, and demo asset portfolios are synthetic. The UI must show a visible "Demo data" label wherever they appear. Demo sites use real public locations (cities, ports, airports) but represent no real company's facilities and must say so.
- Respect source terms: declared User-Agent for NWS, a free key for NASA FIRMS, an approved appname for ReliefWeb, robots.txt for news pages, publisher copyright (store snippets only).
- Tenant asset locations are confidential business data. Never visible across tenants, never used for model training, never written to logs.

**Four problems the engine solves**

| Problem | Input | Output | Method |
|---|---|---|---|
| A. Place mention linking | Article text | Mentions linked to place or facility entities with coordinates | BELA, type filter on Wikidata classes, coordinates joined from Wikidata |
| B. Fallback resolution | Mentions BELA rejects or links to non-places | Gazetteer place or unresolved | GeoNames and alias lookup, context features, optional BLINK or LLM adjudication |
| C. Event location | All resolved places in an article | One event location with an uncertainty radius and confidence | Rule and model based selector using headline position, specificity, hierarchy consistency |
| D. Asset exposure | Event geometry, tenant assets | Exposure records with distance, score, level | PostGIS distance and containment, type and severity weights |

**Pipeline rules**
- Linking and geolocation run once at ingestion and results are stored. Alerts read stored results.
- Mentions that cannot be resolved stay unresolved and are never silently placed on the map. An event with only country-level location is shown as country-level and is not alertable against site assets.
- Article content is untrusted input for the local LLM. See section 10.

### 5.3 Dataset build order and checks

1. `make data` runs all download scripts, writes manifest hashes, and prints row counts.
2. `make etl` produces `data/processed/*.parquet` and loads PostgreSQL.
3. Data quality tests (pandera and SQL assertions): valid coordinates, valid country codes, no duplicate source keys, every place has a type and a country, hierarchy has no cycles, coordinates fall inside the stated country polygon (flag outliers), alias counts, QID and GeoNames cross-link coverage, vector dimension equals 1024.
4. `make seed` loads `data/seed/` (demo tenants, users, demo assets, 90 days of processed incidents and alerts).
5. `make replay` replays archived events through the pipeline at accelerated speed so a demo always shows live-looking alerts, even when no real event is near the demo assets.

## 6. Phase plan

Each phase ends with a demo, a tagged release, and all exit criteria met.

### Phase 0: Foundations and technical spikes (week 1)

**Goal:** remove technical risk before building features.

Tasks
1. Create the monorepo, pre-commit hooks, CI (lint, type check, unit tests, gitleaks, pip-audit, npm audit, U+2014 check), PR template, ADR template.
2. Write `infra/docker-compose.yml` with services: `postgres` (PostGIS plus pgvector image or a custom build), `valkey`, `api`, `worker`, `web`, `nel`, `geo`, `blink`, `llm`, `caddy`, `mailpit`. Health checks on all. Secrets through git-ignored `.env` files and an `.env.example`.
3. **Spike A, BELA on places.** Create a GPU environment. Try the official repository (`facebookresearch/BELA`, MIT) and the community wrapper `multiel` (`pip install multiel`), which loads checkpoints (`wiki`, `aida`, `mewsli`, `e2e`) from the Hugging Face repo `wannaphong/BELA`. Review and pin the wrapper, vendor the code if needed. Run 100 sentences about incidents: 50 with ambiguous places, 20 with facilities, 30 in other languages. Record: VRAM, passages per second, default thresholds (mention 0.2, linking 0.4), whether top-k candidates and scores can be returned (patch inference to return the top 10 if not), what entity index ships with the checkpoint, how often linked entities have coordinates in Wikidata, and the rate of places linked to the wrong same-name entity. Output ADR-001: use the bundled index or rebuild an index limited to the place and facility subset by encoding "title plus description" with BELA's entity encoder.
4. **Spike B, BLINK (optional components).** The upstream repository is archived and targets older Python and PyTorch. Build a pinned, isolated container. Run `download_blink_models.sh`. Confirm the cross-encoder can re-rank arbitrary (context, candidate title plus description) pairs. Test a private catalog of 50 synthetic assets with descriptions to see whether the pretrained bi-encoder can link asset mentions (for example "the Rotterdam terminal") without training. Input format uses `[ENT_START]` and `[ENT_END]` markers. Output ADR-002 with a go or no-go for each BLINK feature.
5. **Spike C, local LLM.** Run `llama-server` with Qwen3-4B-Instruct-2507 Q4_K_M (official or reputable GGUF build, verify checksum and license, or convert locally). Test JSON-schema constrained output on 30 prompts (event type and severity, event location choice among candidates, briefing text). Record tokens per second and VRAM.
6. **Spike D, spatial stack and maps.** Load 100 thousand places into PostGIS. Measure radius and containment queries with GiST indexes. Test H3 aggregation. Build a MapLibre page with Natural Earth polygons and a PMTiles basemap for one region. Decide the basemap approach in ADR-003 (Option A or B in section 5.2), including the OpenStreetMap attribution display.
7. **Spike E, feeds.** Pull one day each from USGS, NWS (with the required User-Agent), and FIRMS (with a free MAP_KEY). Record payload sizes, geometry availability, and rate behavior.

Deliverables: running compose stack, five spike reports, ADR-001 to ADR-003, hardware budget, go or no-go note per component.
Exit: all services start with `make up`; BELA links a place in a sentence and the coordinate is joined from Wikidata; PostGIS queries meet latency targets; the map renders; all three hazard feeds return data.

### Phase 2: Database, spatial ETL, and place knowledge base (weeks 3 to 4)

Tasks
1. Create Alembic migrations for the schema below. Enable `postgis`, `vector`, `pg_trgm`, `pgcrypto`.
2. Load Wikidata subset, GeoNames, Natural Earth. Build the unified `places` table: merge Wikidata and GeoNames records through P1566 and then through name plus country plus coordinate proximity (within a distance threshold by place type), with a review list for conflicts.
3. Build the administrative hierarchy (place, admin-2, admin-1, country) using Wikidata P131 and GeoNames codes, with Natural Earth polygons used to validate country and region. Detect cycles and inconsistent parents.
4. Assign each place a **location uncertainty radius** by type (configurable table, initial values): facility 2 km, village 5 km, town 10 km, city 25 km, large city (population above 1 million) 40 km, admin-2 and admin-1 regions use the polygon, country uses the polygon and is flagged country-level. ### Phase 3: Place linking and geolocation engine (weeks 4 to 7)

This is the core of the project.

**Services**
- `services/nel`: loads BELA once, exposes `POST /v1/link` with input `[{id, text, lang}]` and output per mention: `start`, `end`, `surface`, `qid`, `md_score`, `el_score`, `candidates[{qid, score}]` (top 10). Also `POST /v1/embed` for bge-m3. Batching, fp16, backpressure, `/health`, `/metrics`.
- `services/geo`: library plus HTTP wrapper for gazetteer lookup, context re-ranking, and event location selection.
- `services/blink` (optional, behind feature flags): `POST /v1/rerank` for English place candidates, and `POST /v1/link_assets` for a tenant private catalog. Disabled if the phase 0 spike says no-go.
- `services/llm`: llama.cpp server, chat-completions HTTP endpoint on an internal network only. A thin client enforces JSON-schema output, temperature 0, token limits, timeouts.

**Pipeline (worker tasks)**
1. Chunk articles to the encoder's maximum length at sentence boundaries with small overlap. Pre-filter with an incident topic classifier (bge-m3 plus keyword rules) to control cost, and measure recall loss on the event gold set.
2. BELA mention detection and linking. Keep spans above the mention threshold.
3. **Type filter:** look up each linked QID in `places`. Keep entities that are geographic or facility types and have coordinates. Mentions linked to non-geographic entities (for example a person who shares a place name) are discarded or sent to fallback.
4. **Routing** (initial values, calibrate on the gold set):
   - Accept: `el_score` at or above 0.70, top-1 margin at or above 0.15, and the entity is a geographic type.
   - Adjudicate: `el_score` between 0.40 and 0.70, or margin below 0.15.
   - Fallback: below 0.40, a non-geographic link, or no link for a capitalized span that matches a gazetteer name.
5. **Context re-ranking** for adjudicated and fallback mentions: build candidates from BELA's top 10, trigram and alias search, and bge-m3 search. Features: BELA score, name match type, population prior, country named in the article, outlet country (from GDELT), consistency with other mentioned places (same region or country), explicit qualifiers ("Springfield, Illinois"), distance to the cluster of other mentions, alias language. Combine with a small gradient boosting model trained on the dev split of the gold set.
6. **LLM adjudication** for cases still ambiguous (top two candidates within a small margin): the local model receives the sentence, the mention, five candidates with descriptions, and the article country hints, and returns `{choice: place_id | NIL, confidence, reason}`. Store every candidate and score in `mention_candidates` for the transparency panel.
7. **Event location selection (problem C):** from all resolved places in the headline and lead, choose the event location. Features: position (headline, first sentence), preposition cues ("in", "near", "at", "outside"), specificity (facility above city above region above country), count of mentions, hierarchy containment (prefer the most specific place that is consistent with the others), distance from the outlet country. Train a gradient boosting model on the event gold set, with a rules fallback. Output geometry, `location_level`, uncertainty radius (from the place table, widened when the event spans several places), and a calibrated confidence.
8. **Calibration:** isotonic or Platt calibration per route and for event location confidence, with reliability plots.
9. **Optional BLINK features:** English re-ranking of the top candidates with the cross-encoder when BELA and the gazetteer disagree; asset mention linking for tenants (a private catalog of asset names and descriptions, so "our Dayton plant" or "the Rotterdam terminal" ties to an asset directly).

**Baselines and evaluation harness** (`make eval`)
- Systems: (1) largest population in GeoNames matching the string; (2) GeoNames with country and region context heuristics; (3) GDELT's own extracted locations on the same articles; (4) BELA alone; (5) BELA plus gazetteer fallback plus context re-ranking; (6) system 5 plus LLM adjudication; (7) system 6 plus BLINK re-ranking (if enabled); (8) the full pipeline with event location selection.
- Data: EUPEG corpora, the mention gold set (per language and per ambiguity class), the event gold set, optional Mewsli-X sanity check.
- Metrics: toponym detection F1; place accuracy at 1 where Wikidata or GeoNames gold exists; accuracy within 25 km and within 161 km; median and mean error distance; area under the error-distance curve; event location accuracy at 25 km and 161 km; event type and severity F1; NIL handling; share routed to each route; throughput (passages per second); p50 and p95 latency.
- Output `docs/eval/report.md`, a CSV per run, and `public/metrics.json` for the website.
- Initial targets (confirm or revise with evidence): hybrid beats the best baseline by at least 5 points of accuracy within 161 km on the ambiguous subset; median error of at most 25 km on the event gold set for facility and city level events; BELA stage at least 20 passages per second on the target GPU; at most 25 percent of mentions needing LLM adjudication.

Deliverables: services, pipeline library, tuned thresholds in versioned config, evaluation report, model card (`docs/model_card.md`) covering data, intended use, limits, failure modes (small places, common names, outlet country bias).
Exit: evaluation report committed; thresholds and calibration frozen as `geo_config_v1`; 10,000 article throughput test passes.

### Phase 4: Event pipeline and exposure scoring (weeks 6 to 8)

Tasks
1. **Hazard normalizers:** convert USGS, NWS, FIRMS, and optionally ReliefWeb records into the common `events` schema with source IDs for idempotent updates and revisions. Map fields to type and severity through a versioned rules table (for example magnitude and depth for earthquakes, CAP severity and certainty for weather, cluster size and radiative power for fires). Confirm field names in each source documentation.
2. **News event classification:** the local LLM labels the headline and lead with an event type and severity (1 to 4) using a JSON schema. Types: industrial accident (fire, explosion, spill), natural hazard (flood, storm, earthquake, wildfire, heat, volcanic), transport disruption (port, airport, road, rail closure, accident), labor action, civil unrest, security incident, infrastructure outage (power, telecom, water), health outbreak, other, none. Drop reports about a named private individual. Article text is wrapped in delimiters and treated as data only.
3. **Event clustering and deduplication:** group reports of the same incident using H3 cell neighbors, a time window (default 48 hours, configurable by type), type compatibility, and title embedding similarity. Merge news and hazard feed records into one event with multiple sources. Event status: `new`, `developing`, `ongoing`, `resolved` (after a quiet period).
4. **Cross-confirmation:** news reports near a hazard feed event raise confidence; a news-only event with a single low-reliability source stays as "unconfirmed". Define source reliability weights in config.
5. **Exposure computation:** for each event and each tenant asset, compute distance with PostGIS geography functions, containment in polygon assets and watch zones, and route distance for polyline assets.
   - `proximity = 1` if the asset is inside the event uncertainty region, else `exp(-(distance_km - uncertainty_km) / lambda_type)` where `lambda_type` is configured by event type (for example 5 km for fire and explosion, 25 km for flood and storm, 100 km for earthquake by magnitude class, 15 km for strike and protest).
   - `exposure = type_weight * severity_weight * proximity * location_confidence * source_reliability * recency_decay * criticality_factor`
   - Defaults: severity weights for levels 1 to 4 of 0.15, 0.35, 0.60, 0.85; criticality factor from the asset criticality 1 to 5 as 0.6, 0.8, 1.0, 1.2, 1.4; recency half-life of 24 hours for fast events and 72 hours for slow events.
   - Levels: critical at 0.70 or above, high 0.50 to 0.69, medium 0.30 to 0.49, low below 0.30. Show every component in the UI. Country-level events are not matched against site assets.
6. **Alerts:** create an alert when an exposure crosses the tenant rule threshold, when severity or confidence of an existing event increases, or when an event updates materially. De-duplicate per asset and event, with an update (not a new alert) when only details change.
7. **Evaluation of event labeling and exposure:** event type and severity F1 on the event gold set; exposure alert precision and recall on synthetic scenarios with known true nearby assets; detection delay measured against hazard feed times for events that have both.

Deliverables: normalizers for each feed, news classifier, clustering logic, exposure library with tests, rules and weights in versioned config.
Exit: end-to-end test: ingest a fixture article about a plant fire in an ambiguously named town and a USGS fixture; both create events at the correct locations, merge when appropriate, and an alert appears for the nearest asset and not for a same-name decoy asset.

## 10. Security, authentication, and authorization specification

**Authentication**
- Passwords: Argon2id with tuned parameters, minimum 12 characters, zxcvbn strength check, common password rejection, no composition rules that reduce entropy.
- Login protection: per-account and per-IP rate limits, progressive delay, temporary lockout, generic error messages, audit entries for failures.
- MFA: TOTP (pyotp) with QR enrollment, 10 single-use recovery codes stored hashed. Mandatory for platform admin and tenant admin roles.
- Tokens: short-lived access JWT (10 to 15 minutes, EdDSA) in an httpOnly, Secure, SameSite=Strict cookie. Refresh tokens are opaque random values stored hashed, rotated on every use, with reuse detection that revokes the whole session family. Absolute session lifetime and idle timeout configurable.
- CSRF: double-submit token for state-changing requests; the web app proxies `/api` to keep a single origin.
- Password reset: single-use, time-limited, hashed tokens; no account enumeration.
- API keys: random prefix plus secret, stored hashed, shown once, scoped to permissions and tenant, with expiry and last-used tracking.

**Authorization (RBAC with tenant scoping)**

| Permission | viewer | analyst | manager | tenant admin | finance analyst | platform admin |
|---|---|---|---|---|---|---|
| View map, incidents, alerts, assets | yes | yes | yes | yes | no | yes |
| Acknowledge and dismiss alerts, create watch zones | no | yes | yes | yes | no | yes |
| Upload and edit assets | no | no | yes | yes | no | yes |
| Manage alert rules, view analytics, create reports | no | no | yes | yes | no | yes |
| Manage users, API keys, webhooks, risk config | no | no | no | yes | no | yes |
| View audit log (tenant) | no | no | no | yes | no | yes |
| View platform revenue | no | no | no | no | yes | yes |
| Manage tenants, platform settings, correction review queue | no | no | no | no | no | yes |

Enforce on the server with dependency-injected permission checks and PostgreSQL Row Level Security. The frontend hides unavailable actions but never relies on hiding for protection. Add automated tests for every role against every endpoint group and for cross-tenant access attempts, including spatial queries and map tile or GeoJSON endpoints.

**Data protection**
- TLS 1.2 or higher everywhere with HSTS. Encrypted disk volumes for the database host. Keys loaded from environment secrets, never committed.
- Asset locations are confidential: tenant-scoped through Row Level Security on every spatial query and aggregate, excluded from logs, metrics labels, error messages, and analytics shared across tenants. Emails and webhooks contain asset names and coordinates only when the tenant enables it (default: asset name and distance, no coordinates).
- Tenant data is never used to train or evaluate models without an explicit tenant setting. Correction feedback used for the gold set is stored only with opt-in and stripped of tenant identifiers.
- Data minimization: store snippets and extracted mentions, not full article text. Retention settings per tenant with a scheduled purge job.
- Logs must never contain passwords, tokens, coordinates of tenant assets, or uploaded file contents. Structured logs with request IDs.
- Tamper-evident audit log: append-only table with a hash chain, verification job, no update or delete permission for the application role.
- Upload safety: file size and row limits, coordinate range validation, GeoJSON complexity limits (vertex count), formula injection protection on exports (prefix cells that begin with =, +, -, @), content type checks.
- Webhooks: HMAC signatures with rotating secrets, timeouts, HTTPS only, block private and link-local address ranges (SSRF protection), delivery log.
- Security headers: strict Content Security Policy (allow only the self-hosted tile and style origins), X-Content-Type-Options, frame protections, Referrer-Policy, Permissions-Policy. CORS disabled by default (same-origin).
- Dependency and image hygiene: pinned versions, lock files, Trivy and gitleaks in CI, non-root containers, read-only file systems where possible, internal-only networks for the database, queue, and model services.

**LLM and pipeline safety**
- Treat all article text as untrusted. Wrap it in explicit delimiters, instruct the model to treat it as data, constrain output with a JSON schema, disable tools and network access for the model, cap token counts, and validate outputs before storage.
- The LLM never makes the final alert decision alone. Its outputs are inputs to scores and are always shown with the evidence. Briefing text is validated against stored fields.
- Record model name, version, prompt version, and configuration version on every stored decision.
- Fetcher safety: block private IP ranges (SSRF protection), enforce response size and time limits, sanitize extracted text, honor robots.txt.
- Feed safety: validate every hazard payload against a schema, bound geometry sizes, and ignore records outside plausible ranges.

**Responsible use**
- Disclaimer on map, alert, briefing, and report pages (section 2). Wording on events cites the source, the time, and whether the event is confirmed by a second source or only reported.
- Hazard sources are shown with their own status. Never present an automated feed record as a verified fact. Direct users to official channels for safety decisions.
- No tracking of individuals. Civil unrest events are described at the level of place, time, and reported disruption, without naming or profiling participants.
- A visible correction process for wrong locations and types, with response tracking.
- Error analysis (common place names, small places, outlet country bias, languages with thin coverage, transliteration variants) documented in `/methodology` and `docs/model_card.md`.
