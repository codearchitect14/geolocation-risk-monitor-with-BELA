# Database tuning (phase 10)

Signals are situational awareness derived from public news and public data feeds. They are not official warnings. Verify with local
authorities and follow their guidance.

Measured on the development machine (Apple M5 Pro, PostgreSQL 17 with PostGIS and pgvector, one API process) with 101 synthetic
tenants and 55,000 synthetic assets added to the existing development data (525,000 places, 83,000 assets in total). The plans of the
twenty slowest statements are in `docs/db_tuning_plans.md`, generated by `infra/perf/slow_queries.py` from `pg_stat_statements` after
the load test in `docs/perf.md`.

## What the review found and changed

| Finding | Evidence | Change | Effect |
|---|---|---|---|
| Every request opened two new database connections (one to authenticate, one for its transaction). | Connection set up, SCRAM, and backend start on every call. | Process wide pool (`psycopg_pool`, 2 to 24 connections, `MS_DB_POOL_*`); connections are rolled back before reuse, which also ends the role and tenant context set with `SET LOCAL`. | Capacity at 50 users with no think time rose from 220 to 335 requests per second; median under that load fell from 220 to 140 ms. |
| Tenant queries scanned whole tables. The Row Level Security policy `tenant_id = app_tenant() OR app_bypass()` contains an OR with a row independent test, which cannot become an index condition. | The asset list plan was `Seq Scan on assets`, 82,864 rows removed by the filter, 21 ms for 201 rows. | Platform staff run as a separate role (`meridian_platform`, member of `meridian_app`) with its own allow-all policy; the policy for tenant requests is the plain equality. Added `assets_tenant_page_ix (tenant_id, status, created_at DESC, id DESC)` for keyset paging (migration 0012). | The same query is an index scan of 201 rows: 7 ms, and it no longer grows with the table. Map asset pages fell from 41 ms to 3 ms median under load. Capacity rose to 429 requests per second. |
| Tenant isolation must not weaken. | | The RLS suite (9 tests), the tenancy suite (10 tests), and the role matrix (6 roles by 56 requests) pass unchanged; the full API suite is 376 tests. | |

Combined effect at the realistic load (50 users with 1 to 3 seconds of think time): aggregate median 37 ms to 4 ms, p95 55 ms to 10 ms.

## Statements after the change

The slowest statements under the realistic load are all below 10 ms mean. The top of the list is place name search (trigram and
alias union, 8.8 ms mean over 242 calls, which is the documented target of under 100 ms p95), the login update (one per sign in), and
the asset search. Nothing else exceeds 3 ms. The first line of each plan in `docs/db_tuning_plans.md` shows the access path.

## HNSW `ef_search`

`infra/perf/hnsw_sweep.py` measures recall against an exact scan and latency for several values of `hnsw.ef_search` on 768,000
embedding rows.

Measured with 30 random query vectors, top 10, against an exact scan. Latencies include a cold cache at the first values, so the
low `ef_search` rows are noisier than the others.

| ef_search | Recall at 10 | p50 ms | p95 ms |
|--:|--:|--:|--:|
| 10 | 80.0% | 28.1 | 46.0 |
| 20 | 83.7% | 13.0 | 23.2 |
| 40 | 90.3% | 27.2 | 54.2 |
| 60 | 93.7% | 18.5 | 31.6 |
| 100 | 94.0% | 34.7 | 52.4 |
| 200 | 97.3% | 76.5 | 104.4 |
| 400 | 98.3% | 126.2 | 206.7 |

The configured value stays at 100: it is the knee of the curve (94% recall; doubling it costs twice the latency for 3 points).
Vector search is one of several candidate sources for linking and the candidates are re-ranked, so a missed neighbor is usually
covered by the name and alias indexes. Raise it for batch evaluation runs where latency does not matter.

## Partitioning `events` by month

Not done. The table holds 255 rows in development and the stored production-scale estimate is a few hundred thousand rows a year
(news plus feeds). The queries that matter filter by time and bounding box and use the existing indexes; partitioning would add
complexity (the primary key must include the partition key, and the foreign keys from `event_sources`, `event_updates`, and
`exposures` would need rework) without a measured benefit. Revisit when `events` passes about 5 million rows or retention purges
become slow; partition by `first_seen_at`.

## Connection settings

| Setting | Value | Reason |
|---|---|---|
| API pool | 2 to 24 per process | enough for the default thread pool (40) because most requests hold a connection for under 10 ms |
| Pool wait | 8 s | a request fails rather than queues for long when the pool is exhausted |
| Idle connection lifetime | 300 s | releases connections after a quiet period |
| Connection check on checkout | enabled | a restarted database does not produce a burst of errors |

Size PostgreSQL `max_connections` for processes times pool maximum plus the worker, the harvest jobs, and administrative sessions.
